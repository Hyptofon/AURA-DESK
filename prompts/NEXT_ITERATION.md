# AURA DESK — Continue Next Roadmap Task

Продовжуй розробку AURA DESK відповідно до фактичного стану репозиторію та документації.

## 1. Context Recovery

Перед початком:

- Прочитай `AGENTS.md` і застосовні `.agents/rules/`.
- Завантаж тільки skills, необхідні для поточного завдання.
- Прочитай `docs/ROADMAP.md`, `docs/PROGRESS.md` і відповідні архітектурні документи.
- Перевір поточну гілку, `git status`, останні коміти та фактичну реалізацію.
- Врахуй останні завершені завдання, відомі ризики та blockers.

Не вгадуй контекст і не вважай запис у roadmap доказом готовності функції без перевірки.

## 2. Task Selection

Обери **рівно одне наступне незавершене завдання** з виконаними залежностями.

Перед реалізацією коротко повідом:

- Task ID і назву.
- Назву feature-гілки (формат `feat/<task-id>-<desc>`, `fix/...`, тощо).
- Поточний стан.
- Що саме потрібно реалізувати.
- Які файли потенційно зміняться.
- Основні ризики.
- Які дешеві перевірки будуть виконані.
- Чіткі acceptance criteria.

Створи окрему feature-гілку від актуальної `main` перед внесенням змін.
Не розширюй scope без необхідності. Не починай друге завдання після завершення першого.

## 3. Engineering Standards

Суворо дотримуйся:

- SOLID, KISS, DRY, YAGNI.
- SRP, separation of concerns і dependency inversion там, де це обґрунтовано.
- TypeScript strict, зрозумілих типів та явних контрактів.
- Модульної архітектури, визначеної в `docs/ARCHITECTURE.md`.
- Правил безпеки Electron і вузьких IPC-контрактів.
- Дизайн-системи `DESIGN.md` для будь-яких UI-змін.
- Мінімальних diff без непов'язаного рефакторингу.

Не створюй абстракції заради абстракцій. Не додавай залежності без реальної потреби. Не переписуй працездатний код без причини.

## 4. Git Policy — ABSOLUTE

**ONE FILE = ONE COMMIT.**

Це правило стосується коду, тестів, конфігурацій, документації та виправлень.

- Кожен файл змінюй і коміть окремо.
- Кожен коміт повинен містити рівно один змінений шлях.
- Використовуй Conventional Commits.
- Перед кожним комітом переглядай staged diff.
- Не обходь Git hooks.
- Не створюй великих змішаних комітів.
- Не використовуй `git add .` або `git add -A`.
- Не переписуй історію, не роби squash або rebase.
- Публікація feature-гілки на GitHub (`git push -u origin <branch>`) та відкриття Pull Request є обов'язковими згідно з `docs/DEVELOPMENT_WORKFLOW.md`.
- **Автоматичний merge у гілку main суворо заборонено.** Злиття здійснюється лише після незалежного review (ChatGPT) та явного дозволу користувача.

Після виконання перевір історію через `scripts/verify-one-file-history.py`.

## 5. Tests & Token Efficiency

Самостійно запускай тільки доречні дешеві перевірки:

- Typecheck для зміненого scope або всього проєкту, якщо це дешево.
- ESLint для змінених файлів.
- Targeted unit tests.
- Легкі contract tests.
- Build, якщо це необхідно для поточного завдання.

Не запускай без дозволу:

- Важкі інтеграційні тести.
- Повні E2E-набори.
- Реальні Windows screen/audio hardware tests.
- Платні OpenRouter API-тести.
- Багаторазові або довготривалі тестові цикли.

Якщо потрібна ручна перевірка, надай точну команду, очікуваний результат і критерій PASS.

Не позначай непроведений тест як PASS. Усі результати повинні мати реальні evidence.

## 6. Review & Security

Після реалізації:

1. Перевір diff кожного зміненого файлу.
2. Виконай code review відповідно до застосовного skill.
3. Перевір логіку, edge cases і обробку помилок.
4. Перевір безпеку, приватність та можливі регресії.
5. Перевір відповідність архітектурі й дизайн-системі.
6. Виправ підтверджені недоліки окремими однофайловими комітами.

Не приховуй FAIL, skipped tests або blockers.

## 7. Documentation & Progress

Лише після фактичного завершення й перевірки завдання:

- Онови `docs/ROADMAP.md` окремим однофайловим комітом.
- Онови `docs/PROGRESS.md` окремим однофайловим комітом.
- За необхідності онови ADR або іншу документацію окремими комітами.
- Зберігай реальні результати перевірок, а не припущення.

Якщо acceptance criteria не виконані, не позначай завдання як завершене.

## 8. Final Report

Надай стислий структурований звіт:

- Task ID / назва.
- Назва feature-гілки.
- Посилання на створений Pull Request.
- Статус завдання (`IMPLEMENTED` / `IN REVIEW` / `MERGED`).
- Що реалізовано.
- Змінені файли.
- Commit SHA для кожного файла.
- Тести: PASS / FAIL / NOT RUN.
- Результати code review і security review.
- Підтвердження, що автоматичний merge НЕ виконувався.
- Виявлені ризики.
- Blockers.
- Статус roadmap.
- Наступне рекомендоване завдання.

**Після створення Pull Request зупинись і дочекайся незалежного review.** Не починай наступне завдання автоматично.

Пріоритет: коректність, безпека, підтримуваність, мінімальний scope та економне використання токенів.
